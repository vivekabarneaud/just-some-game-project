## Tier 1 — Live bugs

- [x] **1.14 Every tooltip hover leaked a computation (reported from console warnings 2026-08-31).** `Tooltip.show()` called `hasContent()` as an early-out, which reads `props.text` / `props.content`. Solid compiles an inline JSX prop into a **getter**, so that read evaluates the caller's expression — and doing it from an event handler creates any resulting computation with **no owner**, so it is never disposed (`computations created outside a createRoot or render will never be disposed`). Each orphan stays subscribed to whatever it read, so it re-runs on every later store update for the rest of the session. There are **71 Tooltip call sites, ~49 passing reactive text/content**, plus `FramedItemCard`'s `tooltip=` forwarding — so hovering around the UI accumulated them steadily and the app got heavier the longer a session ran. Fixed by dropping the early-out: the render's `<Show when={visible() && hasContent()}>` already gates it, from inside the owner. Guarded by `tooltipOwnership.test.ts` (a source-contract test — there is no component-test setup in this package). **NB the same trap exists for any handler that touches a JSX prop**; a sweep found no other real instance. *S.*
- [x] **1.13 The weather-roll year was a caller argument, and 12 of 14 callers passed the wrong one (found + fixed 2026-08-31).** Weather rolls off `(season, progress, year)`. 12 call sites passed `state.year` (settlement **age**, the UI's "Year N") where the **world** year belongs; only `App.tsx` and `gameState` passed `getGlobalSeason().year`. Prod hides it entirely (prod ignores the argument and reads the wall clock), so in **dev** the sidebar chip, rain canvas, audio bed and crop climate band each rolled different weather. `currentWeatherInfo`'s own docstring warned about this exact thing — fixed twice, never swept. Fix: the three entry points take the whole clock object and derive the year themselves, so no caller can supply it. Dev derives the LOCAL world year (`worldYearOf`, the inverse of `settlementYear`) rather than reading the wall clock, because reading the wall clock would make weather ignore the speed buttons. `cropClimateBand` now shares the same clock (it had been ignoring its own `_state` parameter). Guarded by `weatherClock.test.ts`, including a repo sweep for any second argument. *S.*
- [x] **1.12 The world calendar existed twice and the two copies fought (found + fixed 2026-08-31).** `frontend/src/data/seasons.ts` said 3-day seasons from May 2 2026; `backend/src/services/tick.ts` said 4-day from April 1. On the day it was found the client read **spring, year 11** and the server **autumn, year 10** — and each overwrote the other: the backend tick walked `s.season` forward to its answer (`tick.ts:105-109`), the client's next tick snapped it back (`gameState.tsx:4055-4062`), so a prod player's season ping-ponged across every save/load. Second half of the same bug: the backend assigned `s.year = globalYear` while the client computes settlement **age**. Fixed by moving the calendar into `shared/src/data/calendar.ts` as the single definition (frontend's numbers kept, user call) with `settlementYear()` as the one age rule. Guarded by `frontend/src/data/calendar.test.ts`. *S.*
- [x] **1.11 Raid victory loot silently dropped (found 2026-08-31, fixed with 2.1).** Both raid resolvers inlined `s.resources[key] = Math.min(caps[key], s.resources[key] + amount)`, which only has buckets for gold/wood/stone. `wolf_pack` awards **40 meat**, and meat is a FOOD (`s.foods`, not `s.resources`) — so the grant evaluated to `NaN`, the player got **nothing** for winning, and `resources.meat = NaN` was persisted into the save. Same family as 1.6. Fixed by routing victory loot through `grantReward`, the dispatcher quest- and mission-claims already use (its own docstring records the identical bug being fixed there once before). Guarded by a data test: every raid's `victoryLoot` must name something the game can bank. *S.*

- [x] **1.1 Raid double-apply on reload.** The offline raid resolver (`frontend/src/engine/gameState.tsx` ~3592, server-load path) lacks the `if (ir.combatLog) continue` guard the tick path has (~5622). A raid resolved live but not yet acknowledged (playback unwatched) survives in `incomingRaids`, round-trips to the server, and gets re-resolved on reload: loot or plunder/citizen deaths applied twice. *Fix: add the same guard. S / low risk.*

## Design-pattern audits (not code debt, but the same "find every instance" shape)

- [ ] **P.1 Narrative gifts must survive the simulation.** *Principle: if the story hands the player something for a purpose, it must still be there when they go to use it.* Found 2026-08-07: the Lammast chronicle says the neighbours leave a bag of grain at the gate but **the player is granted nothing**, while the Bog Witch's `reeds_bargain` charges `wheat 5` — a resource the citizens eat every hour. So a player can earn the beat, log off, and return to find the payment eaten. **Nothing cheap is immune**: wood burns for winter heating (`FUEL_WOOD_PER_HOUR`), only stone is never auto-consumed. Fixes: (a) accept a *choice* of several common goods so a single shortage never blocks (see the retired side-stories doc (in git) → the narrowing menu), or (b) hand over a real **inventory item** (nothing in the sim eats inventory) where hoarding fits the fiction. **Audit:** sweep every chronicle/quest that *describes* giving the player something and confirm the grant exists; sweep every story gate priced in a sim-consumed resource. Also needs a `grantResource()` primitive on the director-chain API (it currently only has `unlockSeed`/`unlockRecipe`). *M.*

- [ ] **P.2 Cross-storyline gate races.** *Principle: a quest should never require a building whose unlock gate lives on a different storyline.* The storylines advance on independent clocks (settlement by building, story by missions), so any such pairing is a latent race that only bites the players who happen to progress in the wrong order. Found 2026-08-08 via the Alchemy Lab: "Slow Venom" (story Ch1) could only be completed by brewing, while the lab was gated on **settlement** Ch4 — so a story-focused player hit a venomed, undeployable adventurer with no cure, while a building-focused player never noticed. Fixed by hanging the gate off the thing that needs it (`requiresMissionDone: "marsh_clearing"`). **Audit:** sweep every quest whose `condition` needs a building, and check that building's `unlockedAt` is on the same storyline (or on a mission/quest/building prereq rather than a chapter). *S — probably a five-minute check; worth confirming the lab was the only one.*
